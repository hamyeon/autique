## 1️⃣ 자동입찰 오류 수정 내용 공유

- 문제 상황 (D1)
    - 자동입찰 상한이 입찰 단위에 맞지 않을 경우 정상적인 수동입찰도 실패하는 문제 발생
    - 자동입찰 상한이 132,000원인 경매에서 135,000원 또는 140,000원을 수동입찰하면 실효 상한 계산 중 예외 발생
    - 예외 발생으로 입찰 트랜잭션 전체가 롤백됨
- 원인 및 해결 방법
    - 정수 나눗셈에서 음수가 0 방향으로 절삭되면서 실효 상한이 사용자가 설정한 상한보다 커지는 문제 확인
    - `EffectiveCapCalculator`의 정수 나눗셈을 `Math.floorDiv`로 변경
    - 정상적인 수동입찰은 성공하고, 대응할 수 없는 상대 자동입찰은 `CAP_REACHED`로 전환되도록 수정
    - 자동입찰 상한에 5,000원 배수 제한을 추가하지 않고 기존 사용자 입력 방식 유지
- 남은 문제 (D3)
    - 예약 자동입찰 상한보다 시작가를 높인 경우 경매 시작에 실패하는 문제
    - 이번 PR의 수정 범위에는 포함하지 않음

## 2️⃣ 경매 시간 정책 변경

- 변경 목적
    - 졸업발표 현장에서 상품 등록부터 입찰·낙찰까지 전체 서비스 흐름을 시연할 수 있도록 경매 진행시간 단축
    - 짧은 경매에서도 자동입찰 및 구매 Agent의 동작을 확인할 수 있도록 시간 정책 조정
- 경매 공통 정책 변경
    - 최소 진행시간: 1시간 → 2분
    - 연장 발동 구간: 종료 1분 이내 → 마감 전 남은 시간 10초 이하
    - 연장 시간: 기존 `endAt` +3분 → +20초
    - 최대 연장 횟수: 3회 → 1회
    - 최초 경매 등록과 재경매에 동일한 최소 진행시간 적용
- 기존 정책 유지 사항
    - 경매 시작 시각의 미래 조건 유지
    - 기존 경매 연장 대상 유지
    - 경매별 잠금 내부에서 마감 시각을 재검사하는 로직 유지
    - 마감 이후 입찰을 거절하는 로직 유지
- API 명세 변경 사항
    - 기존 API 경로 및 요청·응답 필드 구조 유지
    - `/live` 응답의 `maxExtensions` 값이 3에서 1로 변경
    - API·정책·배포 관련 문서에 변경 사항 반영

## 3️⃣ 스케줄러 주기 변경 및 구매 Agent 실행 분리

- 스케줄러 실행 주기 변경
    - 경매 시작·종료 확인 주기: 1분 → 10초
    - 구매 Agent 스캔 주기: 5분 → 30초
    - 짧은 경매에서도 시작·종료 처리 및 Agent의 경매 탐색이 이루어질 수 있도록 실행 주기 단축
- 기존 실행 구조의 문제
    - 경매 시작·종료 작업과 구매 Agent 스캔이 동일한 단일 스레드 스케줄러에서 실행됨
    - 구매 Agent의 AI 호출 시간이 길어지면 경매 시작·종료 작업도 지연될 수 있음
- 실행 구조 변경
    - 구매 Agent에 전용 단일 스레드 스케줄러 연결
    - 경매 시작·종료 등 나머지 작업은 기존 기본 단일 스레드 스케줄러 사용
    - 구매 Agent의 AI 호출과 경매 시작·종료 작업의 실행 스레드를 분리
    - 구매 Agent 스캔의 중첩 실행 방지
    - 놓친 스캔 실행이 대기열에 누적되지 않도록 처리
- 기존 구조 유지 사항
    - API 서버와 Worker의 역할 및 스케줄러 활성화 조건 유지
    - 구매 Agent의 기존 처리 순서 유지
    - 기존 트랜잭션 및 경매별 잠금 로직 유지

## 4️⃣ 테스트 및 검증 결과 공유

- 자동입찰 오류 수정 검증
    - 실제 API 경로에서 정상적인 수동입찰 성공 확인
    - 현재가·승자·자동입찰 상태(`CAP_REACHED`)·입찰 기록 확인
    - 수정 전 계산기에서 신규 회귀 테스트 6개 실패, 수정 후 모두 통과
- 경매 시간 정책 검증
    - 최초 등록 및 재경매의 최소 진행시간 확인
    - 경매 연장 발동 구간의 경계 조건 확인
    - 최대 연장 횟수 1회 적용 확인
    - 마감 이후 입찰 거절 확인
- 동시성 및 전체 경매 흐름 검증
    - 동시 입찰이 발생해도 경매 연장이 최대 1회만 이루어지는 것 확인
    - 경매 종료 처리 및 주문 생성이 중복되지 않는 것 확인
    - 2분 경매 등록 → 입찰·연장 → 경매 종료 → 주문 생성까지 전체 흐름 검증
    - `/result` 응답의 `WON` 상태 및 `orderId` 확인
- 스케줄러 실행 분리 검증
    - 실제 등록된 cron 실행 주기 확인
    - 구매 Agent 실행 중에도 경매 시작·종료 작업이 실행될 수 있는지 확인
    - 구매 Agent 스캔 중첩 실행 방지 확인
    - 전용 스케줄러 분리를 되돌렸을 때 격리 테스트가 실패하는 것 확인
- 검증 범위 및 한계
    - 관련 단위 테스트·슬라이스 테스트·MySQL 통합 테스트 통과
    - 전체 테스트 스위트는 실행하지 않음
    - FE 연동 및 실제 배포 환경에서의 동작은 아직 검증하지 않음

## 5️⃣ FE 연동 및 배포 환경 반영 사항 논의

- FE 반영 사항
    - 경매 등록 및 재경매 화면의 최소 진행시간을 2분으로 변경
    - 시간 선택 UI, 입력값 검증 및 사용자 안내 문구 수정
    - 경매 연장 조건·연장 시간·최대 연장 횟수 관련 안내 수정
    - 경매 연장 시 서버에서 반환한 최신 `endsAt`을 기준으로 남은 시간 갱신
    - 타이머가 종료되더라도 FE에서 낙찰 결과를 자체 확정하지 않고 서버의 종료 확정 및 낙찰 결과 조회
- 배포 환경 확인 사항
    - 구매 Agent는 기본 비활성 상태이므로 API 서버에서 활성화 필요
    - `PURCHASE_AGENT_SCAN_ENABLED=true` 적용
    - `api.env`의 기존 cron 환경변수가 변경된 기본값을 덮어쓰는지 확인
        - `AUCTION_START_CRON`
        - `AUCTION_END_CRON`
        - `PURCHASE_AGENT_SCAN_CRON`
- 졸업발표 시연 관련 확인 사항
    - 2분 경매에서 상품 등록부터 낙찰까지 전체 흐름이 정상적으로 동작하는지 확인
    - 짧은 경매에서도 구매 Agent가 조건에 맞는 경매를 탐색하고 자동입찰하는지 확인
    - 구매 Agent의 AI 호출이 경매 시작·종료를 지연시키지 않는지 실제 배포 환경에서 확인
    - 변경된 시간 정책을 발표 시연 및 사용자 테스트에 동일하게 적용할지 논의
